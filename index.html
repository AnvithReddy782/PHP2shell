PHP2Shell: Critical PHP Flaws, Remote Code Execution and Fixes

Two serious flaws in PHP can let an attacker run code on a vulnerable server without logging in. Both are rated Critical, at 9.2 out of 10. Here is who found them, what that risk means and how to respond.

A website can be running unchanged application code and still become vulnerable because the PHP runtime beneath it needs patching. That matters for business sites, customer portals and online stores whose PHP versions are easy to overlook.

On October 21, 2026, the PHP project released emergency fixes for two vulnerabilities known as PHP2Shell: CVE-2026-109618 and CVE-2026-109619. Both received a Critical severity rating. Under the right conditions, either flaw can allow someone outside the organisation to run code through an affected PHP process without signing in.

Not every PHP deployment is exposed in the same way. The server interface, PHP version and request-handling setup affect whether a particular exploit works. That distinction matters when deciding what to patch first.

How Serious Is PHP2Shell?

Critical severity 9.2 / 10 Both disclosed vulnerabilities

In plain terms: this is near the top of the security severity scale. Successful exploitation could give an outsider access to code execution and sensitive information on an affected server. The rating is called CVSS v4.0 in security advisories, but the practical point is simpler: identify exposed PHP systems and patch them urgently.

The number describes how serious the flaws can be. It does not mean an attack will succeed against 92% of servers, or that every website using PHP can be compromised in the same way.

What Does Remote Code Execution Mean?

Remote code execution (RCE) means an attacker can make a computer run instructions from somewhere else. In this case, a crafted web request may cause a vulnerable PHP server to run attacker-controlled code without the attacker needing a login. The weakness is in PHP's runtime, not necessarily in the website's own code.

For a business website or customer portal, that could mean reading information available to the PHP process, stealing database credentials stored in the application environment, changing website files or planting malicious code. What an attacker can do depends on the access permissions of that PHP process and the server's configuration. RCE does not automatically mean full administrator control of the machine.

Researchers demonstrated attacks that achieved RCE against test deployments of WordPress, Drupal and Joomla. That shows the potential impact, not that every installation of those products is exploitable. The two PHP2Shell vulnerabilities have different technical paths; they do not have to be chained together for RCE to be possible.

Who Discovered PHP2Shell, and How?

Calif Research, OpenAI and Wiz Research each investigated PHP's memory-handling code and reported related findings. Their work combined AI-assisted code analysis with manual investigation, exploit testing and earlier research into PHP's handling of memory exhaustion.

What role did AI play?

Ryan Austin started with an existing concern: could PHP's handling of memory exhaustion still leave exploitable states? He used AI-assisted analysis to examine the relevant C code, then investigated and tested the failure paths. The starting point was a specific technical question, not a broad automated scan.

Wiz reported using Wiz Atlas, Gemini 4 Argon and GPT-5.6 Sol to examine the PHP engine and help investigate attacks involving applications such as WordPress and Drupal. OpenAI carried out separate research and helped coordinate disclosure. In each case, researchers tested what the code could actually do before treating a finding as a vulnerability.

The earlier Quarkslab finding also matters. A memory-handling concern noted in 2024 took further investigation to turn into a demonstrated security risk. AI helped with the search, but the exploit evidence and remediation came from hands-on security work.

Why PHP Worker Processes Matter

A PHP worker may handle many HTTP requests before it is restarted. That saves resources, but it also means PHP must clean up temporary request data and references correctly before the worker handles another request.

Both PHP2Shell flaws involve memory handling, but they are separate vulnerabilities with different prerequisites. The PHP project highlighted Apache with mod_php as particularly exposed to the demonstrated application-independent attack. PHP-FPM deployments still need patching, even where an identical exploit cannot be reproduced.

CVE-2026-109618: Memory Allocation and Cleanup

Some PHP request-processing code makes internal structures available before their initialisation is complete. If memory allocation fails at that point, error handling can leave those structures in an invalid state. Cleanup code may then access them.

Multipart form submissions can be used to trigger the memory pressure involved in some attack paths. Under the right conditions, the resulting memory corruption can lead to code execution. The risk is more specific than a file-upload buffer being left uncleared, and it varies across server interfaces.

CVE-2026-109619: A Stale Memory Reference

PHP keeps some worker-level state between requests. This flaw can leave that state pointing to memory from an earlier request after the memory has been released. When code later follows the stale pointer, it may access memory it no longer owns. This is a use-after-free bug.

Session upload-progress handling is involved in some reported exploit paths, but other worker-level state is also relevant. Disabling upload progress can close certain paths; it does not fix the underlying bug.

Potential impact: successful code execution normally runs with the permissions of the affected PHP process. Application files, credentials and data available to that process could be exposed. It does not automatically give an attacker administrator access to the whole server.

What Server Teams Should Check

Start with the PHP version actually serving each site, not the version installed on an administrator's laptop or in a staging environment. Include containers, managed hosting accounts and older applications that may have been missed in routine updates.

Patching and Short-Term Workarounds

The October 21 fixes were released as PHP 8.2.35, 8.3.36, 8.4.27 and 8.5.12. PHP 8.1 and older no longer receive routine upstream security updates; move to a supported branch or confirm that your operating-system vendor has backported the fix. A separate Windows PHP package update followed on October 26 for a bundled-library issue.

Installing a fixed PHP build is the only complete remedy for these two CVEs. Where patching cannot happen immediately, the following measures may reduce exposure to particular attack paths. None replaces the update:

  1. Disable session upload progress where feasible. Apply session.upload_progress.enabled=0 in configuration that is effective before request processing, then restart every affected worker. This removes confirmed session-related paths but not all stale-state variants. Verify that the application does not depend on upload-progress tracking.
  2. Review request-size limits. Use appropriate limits at the web server or reverse proxy and control multipart input complexity. Avoid blocking legitimate uploads or application forms without testing.
  3. Consider the PHP memory-limit workaround only with specialist review. The project's advisory discusses memory_limit=-1 as a temporary way to reduce the controllable out-of-memory path. Removing that limit can create availability risks and still does not guarantee protection; enforce suitable operating-system or container resource boundaries as directed by your platform guidance.
  4. Maintain defence in depth. Current WAF rules, process isolation, access controls, logging and narrowly scoped outbound restrictions may help reduce exposure or impact. They cannot be assumed to stop every memory-corruption exploit or data leak.

Recycling PHP-FPM workers through pm.max_requests, or performing a graceful reload without replacing the vulnerable runtime, is not a fix. Confirm the updated build is running and that old workers have exited.

Separate PHP Advisory: October 23

PHP issued another notice on October 23 for CVE-2026-115560. It describes a separate, less common code-execution scenario involving session upload progress and changes to the session serialisation handler during execution. It is not one of the two PHP2Shell flaws. Administrators using that feature should also review PHP's recommendation to disable session upload progress pending the next regular bug-fix release.
